# 낑기타자 운영자 기능·로직 설명서

이 문서는 낑기타자를 처음 운영하는 사람도 화면을 보며 관리할 수 있도록 작성한 내부 안내서입니다. 제품 코드를 직접 수정하는 방법보다, 운영 센터에서 무엇을 확인하고 어떤 순서로 처리하는지를 설명합니다.

현재 확인된 기준은 저장소의 Next.js 화면, Route Handler, Supabase migration입니다. 실제 운영 환경의 URL·데이터·스케줄러 설정은 이 문서에 포함하지 않습니다.

## 1. 로컬에서 운영 화면 열기

### 사전 준비

- Node.js `20.9.0` 이상을 사용합니다. 저장소 검증 버전은 `22.20.0`입니다.
- 저장소 루트에서 패키지를 설치합니다.
- Docker Desktop, OrbStack처럼 Docker 호환 컨테이너 런타임이 실행 중이어야 합니다.
- Supabase CLI `2.109.0` 이상을 사용합니다. 저장소의 `supabase/config.toml`과 migration이 로컬 Postgres·Auth·카탈로그를 구성합니다.
- 현재 컴퓨터의 로컬 연결 값은 `.env.development.local`, 검증된 운영자 로그인 값은 `.env.local-admin.qa`에 있습니다. 두 파일은 Git에서 제외되며 외부로 공유하지 않습니다.

```bash
npm install
supabase start
npm run dev -- --hostname 127.0.0.1
```

개발 서버 기본 주소는 `http://127.0.0.1:3000`입니다.

- 고객 흐름: `http://127.0.0.1:3000/join`
- 운영자 로그인: `http://127.0.0.1:3000/admin`
- 로그인 후 운영 센터: `http://127.0.0.1:3000/admin/dashboard`
- 로컬 Supabase Studio: `http://127.0.0.1:54323`

포트가 이미 사용 중이면 Next.js가 다른 포트를 표시할 수 있으므로 터미널에 나온 주소를 사용합니다. 로컬 개발 서버는 실행 중인 터미널에서 `Ctrl+C`로 종료합니다.

### 현재 로컬 운영자 계정 확인

`.env.local-admin.qa`를 텍스트 편집기로 열어 `ADMIN_EMAIL`과 `ADMIN_PASSWORD`를 확인한 뒤 `/admin`에 입력합니다. 이 파일의 값은 로컬 Supabase 전용이며 프로덕션 계정으로 사용하지 않습니다. 비밀번호를 채팅, 이슈, 스크린샷에 복사하지 마세요. 2026-09-08 실제 로그인과 모바일 대시보드 진입까지 검증했습니다.

로컬 DB를 `supabase db reset`으로 초기화하면 Auth 계정도 삭제됩니다. 이 경우 `http://127.0.0.1:54323`의 Studio에서 `Authentication` → `Users`로 이동해 새 이메일·비밀번호 사용자를 만들고, 같은 이메일을 `.env.development.local`의 `DEV_ADMIN_EMAILS`에 넣은 뒤 Next.js 개발 서버를 다시 시작합니다. 프로덕션에서는 이 절차 대신 승인된 Supabase Auth 계정과 `ADMIN_EMAILS`를 사용합니다.

Supabase를 종료할 때는 저장소 루트에서 `supabase stop`을 실행합니다. 기본 종료는 로컬 데이터를 보존합니다.

### 로컬 확인 순서

1. `/join`에서 활성 승차 지점이 `Spot A` 정확히 하나이고 하차 지점 목록이 보이는지 확인합니다.
2. `/admin`에서 Supabase Auth 계정으로 로그인합니다.
3. `/admin/dashboard`에서 운영 현황과 하차 지점 목록을 확인합니다.
4. 데이터가 비어 있으면 화면 오류라고 단정하지 말고, migration 적용 여부·활성 카탈로그·요금표를 확인합니다.

`/join`이 열리지만 경로가 보이지 않을 때는 먼저 `supabase status`로 로컬 스택이 실행 중인지 확인합니다. 이어서 `http://127.0.0.1:3000/api/catalog`이 `200`과 승차 지점 목록을 반환하는지 확인합니다. `503`이면 Next.js가 원격 또는 중지된 Supabase를 보고 있을 수 있으므로 `.env.development.local`의 로컬 URL과 개발 서버 재시작 여부를 확인합니다.

## 2. 관리자 로그인과 권한

운영 센터 로그인은 Supabase Auth 이메일·비밀번호를 사용합니다. 로그인에 성공해도 관리자 허용 목록에 없는 이메일이면 관리자 API가 거부됩니다.

- 프로덕션 관리자 허용 목록: `ADMIN_EMAILS`
- 비프로덕션에서 `ADMIN_EMAILS`가 비어 있을 때만 쓰는 개발 허용 목록: `DEV_ADMIN_EMAILS`

권한 판정은 서버의 `auth.getUser()` 결과와 허용 목록의 이메일을 함께 확인합니다. 브라우저에서 입력한 이메일이나 사용자 메타데이터만으로 운영 권한을 주지 않습니다. 로그인 후 `/api/admin/data`, `/api/admin/metrics`, 하차 지점 관리 API가 `401`을 반환하면 먼저 세션과 허용 목록을 확인합니다.

### Spot A 단독 파일럿 확인

파일럿 중 고객에게 노출되는 승차 지점은 `spot_a` 하나뿐입니다. `20260908083843_spot_a_only_pilot.sql`을 적용한 뒤 Studio의 `pickup_spots`에서 `spot_a.active = true`, 그 밖의 모든 행은 `false`인지 확인합니다. 기존 대기·매칭의 참조를 보존해야 하므로 다른 승차 지점을 삭제하지 않습니다.

## 3. 운영 센터 화면과 쉬운 사용법

운영 센터에는 다음 다섯 탭이 있습니다.

| 탭 | 하는 일 | 먼저 볼 것 |
| --- | --- | --- |
| 운영 현황 | 현재 대기 인원, 매칭 수, 최근 7일 흐름과 건강 지표 확인 | 대기 인원·가장 오래 기다린 시간·오늘 매칭 수 |
| 하차 지점 | 목적지와 요금표 생성·수정·순서·노출 상태 관리 | 활성 상태와 모든 승차 지점의 요금표 |
| 대기열 | 최근 대기 엔트리 20건 확인 | 경로, 일행 인원, 빠른 출발/요금 절약, 상태 |
| 매칭 기록 | 최근 매칭 20건 확인 | 팀 번호, 총 인원, 상태 |
| 신고 | 최근 신고 20건 확인 | 신고 유형·내용·접수 시각 |

표의 시각은 한국 시간(`ko-KR`, `Asia/Seoul`)으로 표시됩니다. 화면의 데이터는 캐시하지 않고 다시 불러옵니다. 잠시 후에도 값이 이상하면 새로고침하고, API 오류가 반복되면 장애 대응 절차를 따릅니다.

### 3.1 하차 지점 추가

1. `하차 지점` 탭에서 `하차 지점 추가`를 누릅니다.
2. 다음 값을 입력합니다.
   - ID: 영문 소문자·숫자·`-`·`_` 조합, 2~48자 범위의 식별자입니다. 저장 후 바꿀 수 없습니다.
   - 표시 이름: 고객 화면에 보이는 이름입니다.
   - 권역: `중간 권역` 또는 `상단 권역`입니다.
   - 하차 후 도보: 0~60분의 정수입니다.
   - 보조 설명: 고객이 목적지를 구분할 때 보는 짧은 설명입니다.
   - 노출 상태: `초안`, `활성`, `비활성` 중 하나입니다.
3. `승차 지점별 요금표`에서 각 승차 지점의 최소 요금·최대 요금·예상 시간을 입력합니다.
4. `저장`을 누릅니다.

활성화하려면 현재 활성인 모든 승차 지점에 유효한 요금표가 있어야 합니다. 최소 요금은 1 이상, 최대 요금은 최소 요금 이상, 예상 시간은 1 이상이어야 합니다. 요금표가 빠진 상태로 활성화하려 하면 저장이 거부됩니다.

### 3.2 하차 지점 편집·순서·상태

- `편집`: 이름, 설명, 권역, 도보 시간, 노출 상태와 요금표를 수정합니다. ID는 수정하지 않습니다.
- `위로`·`아래로`: 고객 화면에 보이는 순서를 바꿉니다. 저장된 순서는 10 단위의 표시 순서로 관리됩니다.
- `활성화`: 고객의 새 대기 화면에 노출합니다. 모든 활성 승차 지점의 요금표가 완성되어야 합니다.
- `비활성화`: 새 대기 화면에서 숨깁니다. 이미 만들어진 대기열이나 매칭은 바꾸지 않습니다.

삭제 버튼은 없습니다. 과거 매칭·정산이 목적지를 참조할 수 있으므로 운영 중인 목적지는 비활성화하는 방식으로 보존합니다. 목적지 이름이나 요금이 이미 생성된 매칭에 소급된다고 가정하지 마세요. 매칭에는 생성 당시 경로·요금 snapshot이 저장됩니다.

## 4. 매칭 로직을 쉽게 이해하기

### 4.1 대기 풀

`빠른 출발`과 `요금 절약`은 같은 승차 지점·하차 지점 조합 안에서 하나의 대기 풀을 공유합니다. 일행은 나눠지지 않으며, 한 번의 제안에는 서로 다른 대기 엔트리 2개 이상, 총 2~4명만 들어갑니다.

- 총 4명 조합: 즉시 제안합니다.
- 총 2~3명이고 모두 `빠른 출발`: 즉시 제안합니다.
- 총 2~3명에 `요금 절약`이 포함: 가장 오래된 엔트리의 3분 대기 제한이 지난 뒤 제안합니다.
- 후보가 없거나 조건을 만족하지 않으면 계속 대기합니다.
- 오래 기다린 엔트리가 먼저 선택됩니다. 가장 오래된 엔트리가 같은 후보끼리는 4명 만석, 더 많은 인원, 더 적은 일행 수 순으로 우선합니다.
- 3분 제한이 끝날 때까지 가능한 팀이 만들어지지 않으면 해당 엔트리는 `expired`가 됩니다.

서버 DB 함수가 하나의 잠금 안에서 후보를 고르고 팀을 만듭니다. 그래서 동시에 여러 요청이나 스케줄러가 들어와도 같은 엔트리가 두 팀에 중복으로 들어가지 않는 것을 목표로 합니다. 팀 번호는 한국 시간 기준 서비스 날짜별로 순번을 받습니다.

### 4.2 제안과 수락

매칭 엔진이 팀 후보를 만들면 매칭 상태는 `offered`가 되고, 각 참여자에게 20초 제안 시간이 생깁니다. 모든 참여자가 제안을 수락해야 팀이 `assembling` 상태가 되고, 이때 3분 집합 시간이 시작됩니다.

- 한 사람이라도 제안을 거절하면 해당 팀 제안은 취소됩니다. 거절한 엔트리는 취소되고 나머지는 다시 대기로 돌아갑니다.
- 제안에 답하지 않으면 시간이 지난 뒤 응답하지 않은 엔트리는 `paused`가 됩니다. 수락한 엔트리는 다시 대기하며 새 3분 제한을 받습니다.
- `paused` 사용자는 같은 조건으로 `resume`할 수 있고, 원하지 않으면 취소할 수 있습니다.
- 제안·수락·거절은 서버가 현재 상태와 제안 버전을 확인합니다. 오래된 화면에서 누른 버튼은 성공으로 처리되지 않을 수 있습니다.

### 4.3 집합, 도착, 노쇼, 출발

모든 참여자가 수락하면 고객은 팀 화면에서 팀 번호와 승차 장소, 집합 마감을 봅니다. 각 일행이 실제 승차 장소에 도착하면 `승차 지점 도착 확인`을 누릅니다.

- 집합 마감 전에 모든 일행이 도착하면 매칭은 `ready`가 됩니다.
- 집합 마감이 되면 아직 `matched`인 엔트리는 `noshow`로 바뀝니다.
- 마감 시 도착한 서로 다른 일행이 2팀 이상이면 남은 도착자만으로 `ready`가 됩니다.
- 도착자가 2팀보다 적으면 매칭은 취소되고 도착자는 다시 대기로 돌아가며 새 3분 제한을 받습니다.
- `ready` 상태에서 도착한 멤버 중 한 명이 출발 확인을 하면 팀은 `departed`가 되고 도착한 멤버의 상태도 출발 완료로 바뀝니다.
- 출발은 `ready` 상태에서만 가능하며 같은 요청이 반복되어도 이미 `departed`이면 멱등적으로 성공합니다.

### 4.4 노쇼 제한: 실제 적용 규칙

현재 실제로 적용되는 규칙은 다음과 같습니다.

> 최근 24시간(rolling 24 hours) 안에 노쇼 이벤트가 3회 이상인 참여 세션은 30분 동안 새 대기 등록이 제한됩니다.

노쇼 이벤트와 제한 시간은 서버의 `resolve_matching_timeouts()`가 집합 마감 때 기록합니다. 고객의 새 대기 요청은 `blocked_sessions`의 만료 시각을 확인하고, 아직 제한 중이면 거부합니다. 화면에는 반복 노쇼 시 30분 제한 가능성이 안내됩니다.

주의: `src/lib/session.ts`에는 사용되지 않는 보조 함수와 예전 `2회·5분` 주석이 남아 있습니다. 운영 판단은 이 파일의 주석이 아니라 실제 DB 함수와 `/api/queue`의 `blocked_sessions` 확인을 기준으로 합니다. 이 주석은 내부 유지보수 때 정리할 대상이며, 고객에게 2회·5분 정책으로 안내하지 않습니다.

## 5. 출발 후 정산과 신고

### 5.1 정산

팀이 `departed`가 된 뒤 출발한 멤버만 정산 정보를 조회하거나 등록할 수 있습니다.

1. 택시비를 먼저 결제한 한 명이 `제가 택시비를 결제했어요`를 누릅니다.
2. 실제 총요금, 은행, 계좌번호, 예금주를 입력합니다.
3. 다른 출발 멤버에게 계좌와 정확한 일행별 송금 금액이 표시됩니다.

정산은 매칭당 한 건입니다. 처음 등록한 결제자만 자기 정보를 수정할 수 있고, 다른 멤버가 같은 매칭의 계좌를 다시 등록하려 하면 거부됩니다. 실제 총요금은 인원수로 나누되 나머지 원 단위까지 일행 인원에 맞춰 배분하여, 각 일행 금액의 합이 실제 총요금과 정확히 일치합니다. 예금주 이름은 일부 가려서 표시됩니다.

### 5.2 신고

팀 화면의 `문제 신고`에서 다음 유형으로 접수할 수 있습니다.

- 집합 장소에 나타나지 않음
- 등록 인원과 실제 인원이 다름
- 불쾌하거나 위험한 행동
- 기타

신고자는 해당 매칭의 멤버여야 합니다. API는 같은 세션·매칭의 기존 신고를 먼저 찾아 순차적인 반복 제출을 한 건처럼 처리하려고 하지만, 현재 DB에는 이를 강제하는 고유 제약이 없어 동시에 반복 전송되면 중복 신고가 생길 수 있습니다. 운영자는 `신고` 탭에서 최근 20건을 접수 시각 순으로 확인하고, 팀·접수 시각·내용이 같은 항목은 중복 가능성을 함께 검토합니다. 신고를 임의로 삭제하거나 참여자에게 세션 식별자를 전달하지 않습니다.

## 6. 매칭 엔진 실행: 자동과 수동

매칭 엔진은 제안 생성뿐 아니라 만료된 제안·집합을 정리한 뒤 새 후보를 다시 찾습니다.

### 자동 실행

스케줄러는 다음 엔드포인트를 사용합니다.

```text
GET /api/cron
Authorization: Bearer <CRON_SECRET>
```

이 요청은 `CRON_SECRET`이 설정되어 있고 정확한 Bearer 인증이 있을 때만 실행됩니다. 운영 환경에서는 호출 주기, 실패 알림, 담당자를 별도로 기록합니다.

### 운영자가 수동 실행

운영 현황 탭에는 관리자 세션으로 누를 수 있는 두 버튼이 있습니다.

- `만료 상태 정리`: `POST /api/cron`을 호출해 만료된 제안·집합을 정리하고 다시 매칭합니다.
- `매칭 엔진 실행`: `POST /api/match/trigger`를 호출해 같은 서버 매칭 엔진을 즉시 실행합니다.

스케줄러는 별도로 인증된 `GET /api/cron`을 호출합니다. 두 버튼과 스케줄러 모두 같은 서버 권위 엔진을 사용하므로 브라우저에서 직접 DB 상태를 수정하지 않습니다.

수동 실행 전 확인할 것:

1. 대기열과 매칭 탭에서 실제로 정체가 있는지 봅니다.
2. 같은 요청을 짧은 시간에 반복하지 말고 한 번 실행한 뒤 화면을 새로고침합니다.
3. 성공 알림을 확인한 뒤 대기열과 매칭 기록을 새로고침해 상태 변화를 기록합니다.
4. 엔진 오류가 나면 대기열 행을 수동으로 고치거나 SQL을 직접 실행하지 말고, 로그와 시각을 보존해 개발 담당자에게 전달합니다.

## 7. 지표와 개인정보 운영 원칙

운영 현황에는 현재 대기 좌석, 가장 오래 기다린 시각, 전체 매칭 수와 오늘 매칭 수가 보입니다. 최근 7일 지표에는 사용자 흐름 이벤트와 함께 다음 서버 기준 지표가 있습니다.

- 출발 완료 팀 수
- 해결된 팀 수(`departed` 또는 `cancelled`)
- 제안된 엔트리 수와 수락된 엔트리 수
- 대기 등록부터 팀 생성까지의 중앙 대기 시간
- 팀 상태별 건수

브라우저 이벤트는 화면 노출·클릭 의도 신호입니다. 실제 매칭 상태와 출발 성공 여부는 `matches`와 `queue_entries`의 서버 상태를 기준으로 판단합니다. 이벤트의 참여자 식별자는 원문이 아니라 `EVENT_HASH_SALT`로 가명화한 해시를 사용합니다.

`NEXT_PUBLIC_GA_MEASUREMENT_ID`가 설정되면 같은 제품 이벤트를 GA4에도 보냅니다. GA4에는 참여자 ID·세션 원문·대기/팀 URL 식별자를 넣지 않으며, `/admin`에는 태그를 로드하지 않고 광고 개인화 신호는 끕니다. 운영 판단은 계속 서버 상태와 관리자 지표를 기준으로 합니다.

현재 운영 센터에는 정산 미등록 팀을 따로 모아 보는 목록이나 총 사용자·노쇼 전용 카드가 없습니다. 화면에 없는 수치를 추정하지 말고, 필요하면 개발·데이터 담당자에게 별도 확인을 요청합니다.

참여자 운영 원칙:

- 참여자는 7일 수명의 서명된 HttpOnly 쿠키로 식별됩니다.
- 참여자 ID를 URL, 브라우저 저장소, 요청 본문, API 응답에 기록하지 않습니다.
- 운영 대시보드에는 임시 닉네임을 표시하며 세션 식별자를 표시하지 않습니다.
- 정산 계좌는 출발한 같은 팀 멤버에게만 제공하고, 예금주 이름은 가립니다.
- 관리자 API와 `noshow_events`, `settlements`, `blocked_sessions`는 서버 역할로만 접근하도록 보호됩니다.

## 8. 매일 운영 체크리스트

### 시작 전

- 운영자 Auth 계정과 `ADMIN_EMAILS` 허용 목록이 맞는지 확인합니다.
- `/admin/dashboard` 로그인과 다섯 탭 로딩을 확인합니다.
- 활성 하차 지점과 모든 활성 승차 지점의 요금표가 있는지 확인합니다.
- cron 마지막 성공 기록과 오류 알림 상태를 확인합니다.

### 운영 중

- 운영 현황에서 대기 인원과 가장 오래 기다린 시간을 봅니다.
- `offered`가 오래 남아 있으면 제안 만료와 엔진 실행 여부를 확인합니다.
- `assembling` 팀의 집합 마감·도착 현황을 확인합니다.
- 신고 탭의 노쇼·인원 불일치·위험 행동 신고를 확인합니다.
- 매칭 이상이 있으면 데이터 행을 직접 수정하지 말고 팀 번호, 시각, 화면 상태, API 오류를 기록합니다.

### 종료 후

- 최근 매칭 20건의 상태와 최근 신고 20건을 확인하고 특이사항을 인계합니다.
- 정산 미등록 팀은 현재 운영 센터에서 따로 조회할 수 없으므로 화면만 보고 완료 여부를 추정하지 않습니다.
- 운영 지표는 서버 상태와 고객 이벤트를 구분해 해석합니다.
- 제품 이벤트 보존·삭제 작업은 승인된 운영 절차와 백업 확인 뒤에만 실행합니다.

## 9. 장애 대응

### 하차 지점이 고객에게 보이지 않음

1. 상태가 `active`인지 확인합니다.
2. 모든 활성 승차 지점에 최소·최대 요금과 예상 시간이 있는지 확인합니다.
3. 최대 요금이 최소 요금보다 작거나 시간이 1 미만인지 확인합니다.
4. API 오류가 계속되면 migration과 Supabase 연결 상태를 확인합니다.

### 매칭이 멈춘 것처럼 보임

1. 고객 화면의 새로고침·대기 상태와 운영 대시보드의 실제 상태를 비교합니다.
2. 후보가 같은 승차·하차 경로에 2개 이상인지, 총 인원이 4명을 넘지 않는지 확인합니다.
3. `cheap`이 섞인 2~3명 조합은 오래된 엔트리의 3분 제한 전에는 정상적으로 제안되지 않습니다.
4. cron 또는 수동 엔진을 한 번 실행한 뒤 성공 알림과 대기·매칭 상태 변화를 확인합니다.
5. 반복 실패 시 대기·매칭 레코드를 보존하고 개발 담당자에게 전달합니다.

### 로그인 또는 관리자 API가 401

- Supabase Auth 세션이 만료되지 않았는지 확인합니다.
- 이메일이 `ADMIN_EMAILS` 또는 개발 환경에서 허용되는 `DEV_ADMIN_EMAILS`에 있는지 확인합니다.
- 프로덕션에서 `DEV_ADMIN_EMAILS`를 우회 수단으로 사용하지 않습니다.

### 비밀값 노출 의심

즉시 관련 서비스 역할 키, `CRON_SECRET`, `PARTICIPANT_SESSION_SECRET`, `EVENT_HASH_SALT`를 교체하고 배포 환경의 이전 값을 폐기합니다. 로그와 접근 기록을 보존한 뒤 운영 담당자에게 보고합니다. 값 자체를 이슈·문서·채팅에 복사하지 않습니다.

## 10. 데이터 정리와 안전장치

`scripts/pre-deploy-cleanup.mjs`는 새 서비스 시작 전에 승인된 대상의 테스트 데이터를 비우는 파괴적 스크립트입니다. 일상 장애 해결이나 migration 롤백에 사용하지 않습니다.

실행 계약은 다음과 같습니다.

```bash
node scripts/pre-deploy-cleanup.mjs --dry-run
node scripts/pre-deploy-cleanup.mjs --confirm-delete-all-matching-data
```

두 플래그 중 정확히 하나만 선택해야 하며, 두 번째 명령은 실제 삭제입니다. 또한 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, 실제 URL과 정확히 같은 `CLEANUP_SUPABASE_HOST`가 필요합니다.

실제 삭제 전에는 다음을 모두 확인합니다.

- 연결된 Supabase 프로젝트가 프로덕션이 아니라 승인된 정리 대상인지 확인
- 백업·복구 담당자와 복구 시점 확인
- 먼저 `--dry-run`으로 대상 건수 확인
- 삭제 승인과 유지해야 할 데이터가 없는지 확인

스크립트는 신고·제품 이벤트·노쇼 이벤트·정산·대기열·매칭·제한 세션·일별 팀 번호 카운터를 참조 순서에 맞춰 삭제하고, 남은 행이 있으면 실패합니다. 하차 지점·승차 지점·요금표 같은 카탈로그는 삭제하지 않습니다. 실제 삭제는 복구 가능한 백업과 별도 승인 없이 실행하지 마세요.

## 11. 환경 변수 이름과 용도

| 이름 | 용도 |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | 브라우저·서버에서 사용할 공개 Supabase URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 브라우저·서버에서 사용할 공개 anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 Route Handler·운영 스크립트용 서비스 역할 키 |
| `CRON_SECRET` | `GET /api/cron` 스케줄러 인증 |
| `EVENT_HASH_SALT` | 제품 이벤트 세션 가명화 |
| `PARTICIPANT_SESSION_SECRET` | 참여자 쿠키 HMAC 서명, 프로덕션 필수 |
| `ADMIN_EMAILS` | 프로덕션 관리자 이메일 허용 목록 |
| `DEV_ADMIN_EMAILS` | 비프로덕션에서만 사용하는 개발 관리자 허용 목록 |
| `SUPABASE_URL` | 서비스 역할 운영 스크립트의 명시적 Supabase 대상 |
| `TEST_BASE_URL` | 변경형 스테이징 E2E 앱 주소 |
| `TEST_TARGET_ENV` | 변경형 E2E가 정확히 `staging`인지 확인 |
| `TEST_STAGING_APP_HOST` | E2E 앱 hostname 선언 |
| `TEST_STAGING_SUPABASE_HOST` | E2E Supabase hostname 선언 |
| `CLEANUP_SUPABASE_HOST` | 파괴적 정리 대상 hostname 확인 |

실제 값은 이 문서에 기록하지 않습니다. `NEXT_PUBLIC_`가 붙은 값은 브라우저 번들에 포함되며, 나머지 비밀값에는 이 접두사를 붙이면 안 됩니다.

## 12. 상태·용어 사전

### 대기 엔트리 상태

| 상태 | 뜻 |
| --- | --- |
| `waiting` | 매칭 후보로 대기 중 |
| `offered` | 팀 제안이 표시되고 수락을 기다리는 중 |
| `matched` | 제안을 수락했고 집합을 기다리는 중 |
| `arrived` | 승차 장소 도착을 확인함 |
| `paused` | 제안 미응답 후 대기가 잠시 멈춤. 사용자가 재개할 수 있음 |
| `expired` | 대기 제한이 끝났지만 팀을 만들지 못함 |
| `cancelled` | 사용자가 취소했거나 제안이 거절되어 종료됨 |
| `departed` | 팀 출발이 확정됨 |
| `noshow` | 집합 마감까지 도착 확인이 없어 이번 팀에서 제외됨 |

### 매칭 상태

| 상태 | 뜻 |
| --- | --- |
| `offered` | 모든 후보에게 20초 제안 중 |
| `assembling` | 전원이 수락했고 집합 3분 진행 중 |
| `ready` | 출발 가능한 상태. 마감 전 전원 도착 또는 마감 후 2팀 이상 도착 |
| `departed` | 출발 완료 |
| `cancelled` | 제안 거절·만료 또는 도착자 부족으로 취소됨 |

### 기타 용어

- `일행(party)`: 한 번에 함께 등록한 사람들입니다. 일행 단위로만 팀에 들어가므로 일행을 쪼개지 않습니다.
- `엔트리(entry)`: 대기열에 등록된 한 일행의 기록입니다.
- `승차 지점(pickup spot)`: 고객이 모이는 관리 대상 장소입니다.
- `하차 지점(drop zone)`: 목적지 카탈로그의 한 항목입니다.
- `요금 snapshot`: 매칭 생성 당시의 예상 요금·시간·경로를 보존한 값입니다.
- `서버 권위`: 브라우저 화면이 아니라 서버 DB 함수가 상태 전이와 시간을 최종 결정한다는 뜻입니다.
- `멱등성`: 같은 완료 요청을 여러 번 보내도 결과가 한 번 처리된 것과 같게 유지되는 성질입니다.

관련 세부 운영 계약은 [운영 가이드](OPERATIONS.md), 배포 전 확인은 [출시 체크리스트](GO_LIVE_CHECKLIST.md)를 함께 참고합니다.
